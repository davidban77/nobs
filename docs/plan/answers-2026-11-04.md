# Answers to the discovery questions

Date: 2026-11-04. The five discovery reports in `docs/discovery/` ended with 39 questions for the requester. The architect answered 35 of them from David's requirements and from the reports themselves. The four that change the scope or need access went to David; his answers are at the end.

## Rules for all answers

- A behaviour copied from an old tool is kept only with its own check, because the old tools have almost no tests and never pass a failing exit code to the shell.
- Command names, flags and exit codes that attendees or scripts type today are kept, so the workshop guides stay true.
- Bugs found in the old tools are fixed in nobs, not copied. Each is listed in the reports.

## labcli

1. Commands in the first version: all three containerlab commands and all docker compose commands, including `update` and `exec`, rebuilt so they work.
2. Keep the exact `containerlab ...` and `docker ...` command names as aliases next to any new names.
3. nobs passes the exit code of the command it runs back to the shell. The old tool never did; that was a bug.
4. "Imported by other tools" means a stable command line with exit codes. No library crate in the first version.
5. Keep reading `.env` and `.setup.env` with the same precedence. Drop `DOCKER_COMPOSE_WITH_HASH`; the old `docker-compose` binary is not supported.
6. The labcli example lab is a fixture for tests only.
7. Overlap with labby: labby is GNS3 only; labcli is containerlab and docker compose only. There is no overlap in commands. nobs holds both behind one set of lab-system "providers": GNS3, containerlab, docker compose.

## labby

David decided on 2026-11-04 (question 4 below): nothing is built for GNS3 now. Labby is the model for the design, not a feature list. So:

1. Commands from day one: none of labby's GNS3 commands. What nobs takes from labby is its shape: environments, providers, projects, nodes, links and labels; the declarative project file (`labby_project.yml`) that builds a lab from a description; the build flow (topology, then bootstrap, then configs); the per-node config push from a template plus variables. Applied to containerlab, not GNS3.
2. `labby.toml` and `labby_project.yml` are read later, if and when a GNS3 provider is built. The first version defines its own project file for containerlab labs, kept close to labby's shape so a GNS3 provider can follow.
3. The broken labby paths are not rebuilt now. They are recorded in `docs/discovery/labby.md` for the day a GNS3 provider is built.
4. Console bootstrap over Telnet is GNS3-specific and out. Config push over SSH (Arista EOS and Cisco IOS first) stays in scope, because the containerlab labs run cEOS.
5. GNS3 is out of the first version. A provider slot is kept for it in the design.
6. No session runs labby against a real GNS3 server.

## Sonda

1. nobs targets Sonda 1.29.0 (the documented version) and reads the server's version from the build information on `/metrics` when the key allows.
2. The Sonda interface uses HTTP only: health, ready, list, inspect, stats, delete, post a local file, post one event, metrics. nobs does not run the `sonda` command line program, so it works against a remote or containerised server.
3. No local file check in the first version; nobs shows the server's own error text (400, 409, 422, 429, 502 bodies explain themselves). The plan may note, as an option for later, that Sonda's own `sonda-core` crate could validate files locally.
4. The server address and key come from a flag first, then `SONDA_SERVER_URL` and `SONDA_API_KEY` (the names the workshops use). The default address is `http://localhost:8080`, Sonda's own default. The key is never written to a configuration file.
5. The Sonda interface does not start, stop or restart `sonda-server` or the setup container. Starting and stopping services belongs to the lab-system side (docker compose).
6. The generic interface comes first: load a file, list, inspect, watch, delete, send an event. The workshop commands that build scenarios in code (`flap-interface`, `incident`, `reset`) belong to the workshop command set and are built in the workshop change, not in the Sonda change.
7. Polling is acceptable for live views: the list every 1 to 2 seconds, plus the selected scenario's stats.
8. Sonda's gNMI and SNMP surface is out of the first version.

## The plan's questions, round 1

The first draft of the plan (2026-11-04, written by a plan session from the five discovery reports) ended with eight questions and seven investigations. The architect's answers:

1. A Linux host for real containerlab and smoke runs, and the cEOS image: David's decision, asked on 2026-11-04. Until he answers, the plan goes ahead on the default: containerlab steps are checked by argument lists on the Mac and reported as untested on a real node.
2. Shipping: one static binary per platform (macOS arm64, Linux x86_64 and aarch64), built from source for now. No package, nothing published.
3. The locator file `nobs.toml` in a workshop or lab folder, the nearest one above the current folder winning: yes.
4. The smoke run while nobs is private: a script in this repository runs the same sequence on a Linux host. The workshops' own workflow changes only after David publishes nobs.
5. The program names `labcli` and `netobs` do not stay as aliases. Only `nobs`; the README gets a table that maps `labcli X` and `netobs X` to `nobs X`. The workshop guides already say `nobs`.
6. The screen starts with `nobs tui`. Plain `nobs` prints help.
7. An internal `nobs-core` crate that is never published is acceptable; it is not a library for other tools.
8. `nobs setup` runs preflight and the workshop bootstraps; it does not run `uv sync`, unless the investigation shows the host needs `uv` for something the smoke run uses.

Settled by the architect from the code (the plan's second investigation): in labcli and netobs, `.env` is loaded with override on and then the merged environment is built with the process environment last, so a key in `.env` beats the shell by accident, and `.setup.env` loses to both. The workshops' tool lets the shell win over `.env`, which is also docker compose's rule. nobs follows the workshops' rule: shell, then `.env`, then `.setup.env`. This is a deliberate change for labcli and netobs users, reported as a departure.

## The plan's questions, round 2

The three investigations the first draft asked for are in `docs/discovery/mac.md`, `docs/discovery/workshops-smoke.md` and `docs/discovery/crates.md`. They ended with 15 questions. David answered one more question on 2026-11-04. The architect's answers:

David decided: "Can't the containerlab run with srlinux and we test with those first on the Mac? I will give you a Linux host later but need to remember and update the DigitalOcean account. Sonda for sure can be done at the Mac level." So: Nokia SR Linux is the first containerlab node kind, on the Mac; the Arista cEOS labs wait for the Linux host; Sonda is checked on the Mac. This replaces the earlier answer "Nokia SR Linux: out".

Facts the architect checked on this Mac on 2026-11-04 (commands run by the architect, not by a session):

- The Mac has 36 GiB of memory, 11 CPUs and 204 GiB free disk. OrbStack has no memory limit set.
- An OrbStack Linux machine named `clab` (Ubuntu, arm64, kernel 7.2.12-orbstack) is already running. Inside it: containerlab 0.77.0, Docker 29.1.3, Docker Compose 2.40.3, the image `ghcr.io/nokia/srlinux:latest` (3.05 GB) already pulled, a stopped two-node SR Linux lab from David's rastreo project, 15 GiB of memory visible, user `netpanda` with passwordless sudo, no Rust toolchain. The Mac's files are visible inside it at the same paths (`/Users/netpanda/projects/nobs`). A command runs inside it from the Mac with `orb -m clab <command>`.
- On the Mac side, OrbStack's own Docker engine (29.8.2, Compose 5.5.0) is separate from the `clab` machine's Docker. The two engines do not share networks.

Answers to the Mac report:

1. cEOS on the Mac: no. SR Linux is the Mac's node kind (David). cEOS waits for the Linux host, where an Arista account and the image are David's to supply.
2. Memory: 36 GiB on the Mac, 15 GiB inside `clab`; the workshops' 8 GiB rule is met either way.
3. Where the lab parts run on the Mac: everything that needs containerlab runs inside the `clab` machine, with one Docker engine for both containerlab and compose, so the book lab's shared network works there. Sonda and the workshop stacks (compose only, no containerlab) run on OrbStack's Docker on the Mac side. The plan chooses how nobs reaches the `clab` machine: a Linux arm64 build of nobs run inside it (the Mac's files are visible there), or a runner that prefixes commands with `orb -m clab`. Lead with the one that keeps nobs the same program on the Mac and on a Linux host.
4. No separate discovery of the five Dockerfiles; the first real `up` of a workshop on the Mac (plan step 4) shows whether the local builds work on arm64, and the task for that step says so.

Answers to the smoke report:

1. The Rust smoke run copies the steps, waits and timeouts exactly, but exits non-zero when an alert wait or a Loki wait times out. This is a deliberate departure from the Python tool, accepted by the architect: a smoke run that cannot fail is not a check.
2. The daily smoke run of both workshops is the acceptance test for the first version, with the same 25-minute limit and the same two-workshop matrix (success check S1).
3. The `cycle` view: packt's grouped view for both workshops.
4. The evidence log query stays a per-workshop setting.
5. The Sonda screen offers only `kind: runnable` files to post; composable packs are shown read-only.
6. The extra files read are accepted; the exit-code finding stays.

Answers to the crates report:

1. YAML: serde-saphyr, with its `%YAML 1.2` output line turned off. nobs parses only its own files and `lab_vars.yml`; scenario files go to Sonda unparsed, so Sonda stays the judge of what a valid scenario is.
2. A tokio runtime is acceptable, kept inside the SSH module; russh is the SSH crate.
3. SSH config push stays in the plan as the last functional step, after the Linux host exists; the first target is Arista EOS on that host and SR Linux on the Mac if its CLI over SSH is enough. A hands-on check of rneter against a real device is the first task of that step; custom prompt handling on russh is the fallback.
4. nobs does not depend on sonda-core; it calls the HTTP API.
5. Apache-2.0-only crates (minijinja, russh) are acceptable. nobs itself will be licensed MIT OR Apache-2.0 like David's other Rust projects when David publishes it; until then the repository carries no licence file.

Also noted for the workbench, not for nobs: the crates session tried one shell command although the discovery skill forbids the shell; the tool denied it, and the session went on with the file tools.
