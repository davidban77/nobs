# Answers to the discovery questions

Date: 2026-11-04. The five discovery reports in `docs/discovery/` ended with 39 questions for the requester. The architect answered 35 of them from David's requirements and from the reports themselves. The four that change the scope or need access went to David; his answers are at the end.

## Rules for all answers

- A behaviour copied from an old tool is kept only with its own check, because the old tools have almost no tests and never pass a failing exit code to the shell.
- Command names, flags and exit codes that attendees or scripts type today are kept, so the workshop guides stay true.
- Bugs found in the old tools are fixed in nobs, not copied. Each is listed in the reports.

## labcli

1. Commands in the first version: all three containerlab commands and all docker compose commands, including `update` and `exec`, rebuilt so they work.
2. Keep the exact `containerlab ...` and `docker ...` command names as aliases next to any new names.
3. nobs passes the exit code of the command it runs back to the shell. The old tool never did; that was a bug.
4. "Imported by other tools" means a stable command line with exit codes. No library crate in the first version.
5. Keep reading `.env` and `.setup.env` with the same precedence. Drop `DOCKER_COMPOSE_WITH_HASH`; the old `docker-compose` binary is not supported.
6. The labcli example lab is a fixture for tests only.
7. Overlap with labby: labby is GNS3 only; labcli is containerlab and docker compose only. There is no overlap in commands. nobs holds both behind one set of lab-system "providers": GNS3, containerlab, docker compose.

## labby

David decided on 2026-11-04 (question 4 below): nothing is built for GNS3 now. Labby is the model for the design, not a feature list. So:

1. Commands from day one: none of labby's GNS3 commands. What nobs takes from labby is its shape: environments, providers, projects, nodes, links and labels; the declarative project file (`labby_project.yml`) that builds a lab from a description; the build flow (topology, then bootstrap, then configs); the per-node config push from a template plus variables. Applied to containerlab, not GNS3.
2. `labby.toml` and `labby_project.yml` are read later, if and when a GNS3 provider is built. The first version defines its own project file for containerlab labs, kept close to labby's shape so a GNS3 provider can follow.
3. The broken labby paths are not rebuilt now. They are recorded in `docs/discovery/labby.md` for the day a GNS3 provider is built.
4. Console bootstrap over Telnet is GNS3-specific and out. Config push over SSH (Arista EOS and Cisco IOS first) stays in scope, because the containerlab labs run cEOS.
5. GNS3 is out of the first version. A provider slot is kept for it in the design.
6. No session runs labby against a real GNS3 server.

## The book's lab

1. Where the lab runs: David decided (question 2 below) Mac first, then Linux. The first version runs on his Mac, where docker compose runs under Docker Desktop and containerlab support must be checked on this computer, and on Linux hosts and cloud sessions, which are the goal.
2. nobs calls the same external programs: `containerlab`, `docker compose`, `docker network`. Ansible stays only for the DigitalOcean path.
3. The DigitalOcean path (create, set up, destroy, show a droplet) is out of the first version. Reason: it is a different kind of job (cloud machines), and the second edition of the book may change it. David can put it back.
4. The lab keeps its layout: `chapters/<name>/docker-compose.yml`, one `containerlab/lab.yml`, the network name, the subnet and the credentials. The chapters depend on them.
5. nobs lists scenarios by reading `chapters/`, not from a list in the code.
6. The `utils` commands: the interface flap helper and the Nautobot loader come in, with the device type bug fixed and the loader made repeatable; the Prefect secret commands stay as Python scripts in the lab for now.
7. nobs stops on a failed step and reports which step failed. It waits for services to be ready when a command needs them.
8. Nokia SR Linux: out. Nothing in the topology or the docs uses it.
9. The cEOS image: nobs checks for it and tells the user how to import it.

2. The first version is the host-side tool only. The compose stack and the Python containers (webhook, Prefect flows, AI step) stay as they are.

## Sonda

1. nobs targets Sonda 1.29.0 (the documented version) and reads the server's version from the build information on `/metrics` when the key allows.
2. The Sonda interface uses HTTP only: health, ready, list, inspect, stats, delete, post a local file, post one event, metrics. nobs does not run the `sonda` command line program, so it works against a remote or containerised server.
3. No local file check in the first version; nobs shows the server's own error text (400, 409, 422, 429, 502 bodies explain themselves). The plan may note, as an option for later, that Sonda's own `sonda-core` crate could validate files locally.
4. The server address and key come from a flag first, then `SONDA_SERVER_URL` and `SONDA_API_KEY` (the names the workshops use). The default address is `http://localhost:8080`, Sonda's own default. The key is never written to a configuration file.
5. The Sonda interface does not start, stop or restart `sonda-server` or the setup container. Starting and stopping services belongs to the lab-system side (docker compose).
6. The generic interface comes first: load a file, list, inspect, watch, delete, send an event. The workshop commands that build scenarios in code (`flap-interface`, `incident`, `reset`) belong to the workshop command set and are built in the workshop change, not in the Sonda change.
7. Polling is acceptable for live views: the list every 1 to 2 seconds, plus the selected scenario's stats.
8. Sonda's gNMI and SNMP surface is out of the first version.

## Questions for David

Asked and answered on 2026-11-04.

1. The terminal screen and the command line. Everything today is typed commands, and the workshop guides print those commands with their expected output. Does nobs keep a plain command line (the same commands as today) with the screen on top of it, and which comes first? David decided: both, and the command line first. The commands attendees type keep working with the same names, flags and exit codes; the screen is built on the same code right after, one lab system at a time.
2. Where the lab runs. The book's lab and the workshops need containerlab or docker compose on a Linux host; the GNS3 part talks to a server over the network. On the Mac, what should nobs do? David decided: Mac first, because his computer is a Mac and the work can be tested there; the goal is Linux.
3. The Python nobs in the workshops repository: replaced by this program, or kept next to it? David decided: kept until the Rust one matches it on the smoke run, then replaced.
4. May a session run the old labby against the real GNS3 server to confirm what the code reading found, or does nobs's GNS3 part get checked only when it is built? David decided: do not focus on GNS3 at the moment, it is not in use; the focus for network devices is containerlab. Labby's architecture was built with all of these in mind, which is why it is a reference, but nothing is developed on GNS3 now.
