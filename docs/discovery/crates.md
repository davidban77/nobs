- serde-saphyr 2.1.0 does both reading and writing (`to_string`). Its README says it shares no code with serde_yaml and is tested against the YAML test suite. It has 1,223 commits and over 4,000 tests. GitHub shows 242 stars, 1 open issue and 1 open PR. Its repo is bourumir-wyngs/serde-saphyr.
- serde-saphyr differs from serde_yaml in these ways:
  - Duplicate keys are an error by default.
  - YAML 1.1 booleans (`yes`/`no`) are accepted for `bool` fields unless `strict_booleans` is set.
  - Merge keys are expanded.
  - Output starts with a `%YAML 1.2` line unless `no_lang_directive` is set.
  - Comments are not captured.
- sonda-core's optional YAML dependency is serde_yaml_ng (docs.rs/sonda-core, read 2026-11-04).

## Reasoned conclusions

- **CLI: clap with `derive` and `env` features, plus clap_complete.** It is the clear leader on maintenance and use (facts 1). Check the nested-group, alias and env features against the clap reference before the plan relies on them.
- **YAML: do not use serde_yaml.** Its repo is archived with a "no longer maintained" notice. serde_yml is also unmaintained. The plan's belief is confirmed.
  - **serde-saphyr is the only serde-based option with a recent release, an active repo and read plus write.** It is a different library, not a drop-in fork. The duplicate-key, YAML 1.1 boolean and `%YAML 1.2` behaviours above matter for lab files that are read and then rewritten.
  - **serde_yaml_ng is the drop-in choice.** It matches the crate sonda-core uses, so nobs and Sonda parse files the same way. Its last release was 2024-05.
  - The decision is therefore about parsing differences versus maintenance. I recommend serde-saphyr, but that recommendation rests partly on judgement. The evidence is a single recent maintainer and a one-line README comparison, not a test of David's real files.
- **TOML: toml.** Nothing in the data contradicts it.
- **Templates: minijinja fits the plan better than tera for "Jinja-style".** I did not compare syntax coverage, so that is a judgement. Its licence is Apache-2.0 only, so confirm David accepts that. Both are on a fresh major version, so pin an exact version.
- **HTTP: ureq 3 fits a synchronous first version.** reqwest blocking would pull in an async runtime. Sonda's own client is still on ureq 2, so using ureq 3 would mean two ureq versions if nobs also depends on sonda-core with the HTTP feature. I did not check whether that is a problem.
- **SSH: russh is the only actively maintained pure-Rust SSH client, but it is async.** ssh2 is blocking but binds a C library, which conflicts with the plan's musl static-binary convention. I did not verify that conflict, only the C binding. A tokio runtime would also be needed for russh.
- **Prompt handling: no mature crate exists.** rneter is the closest match to Arista EOS plus Cisco IOS, but it is young and its backend is unconfirmed. Treat the prompt layer as probably custom code on top of russh, or as a dependency risk. Whether rneter is good enough needs a hands-on test, which this task did not cover.
- **Terminal: ratatui 0.30.x with its default crossterm 0.29 backend.** Crossterm has had no release for 19 months, which is a risk to watch rather than a block.
- **Prometheus text: prometheus-parse is usable but dormant.** For reading a few Sonda metrics, a small custom parser is also plausible. I did not weigh the two.
- **Sonda dependency:** sonda-core has public validation and compile functions and the right licence (MIT OR Apache-2.0, same as David's other crates). But it has no stated stability promise, it is a heavy optional-dependency set, and it releases about every 2–3 days. Using its `compiler` module would couple nobs to Sonda's scenario version, which also means Sonda defines what a valid scenario is. The alternative is to send the file to the Sonda server for validation, which I did not check (no HTTP API reference read).
